# Genuine Source outcome expiry and Android uncertainty retention

Both private production-chain cases pass with actual Pi 1.4.0, Host/relay, local
maintenance IPC and Android repository instrumentation. Native and qualified RPC
retain their distinct supported normal idle reload paths and actual Source owner
binding. Public paged/outcome capabilities remain off; no personal Host or ledger
is used.

The original editor starts with a real paged 1-MiB Source. Android edits the first
bounded window and stores its exact complete possible-write attempt. The genuine
Source ACK and actual SDK result prove the submitted 1,048,576-byte value with hash
`900dce5cc5d1bc1b5f209c09f600c445e85149e116e2b87542913b07d06f1763`.
The Host persists the exact authenticated applied tuple before the fixture drops
its correlated client response. Normal idle reload installs a new Source peer in
the same process/session. Fresh work opens a genuinely distinct incarnation;
using that incarnation in the old receipt returns unknown while the original
applied record still exists.

Only then the fixture adds 31 explicitly metadata-only pending reservations in the
same device scope. These padding entries are not Source SDK writes. A direct
ledger admission at 32 entries fails with capacity; the instrumented editor-owner
contact counter is unchanged across this padding/admission probe. The private
ledger monotonic clock advances by more than 30 days; the admin confirmation clock
remains real process time. This simulates retention, not thirty actual calendar
days of uptime or an allowed wall-clock shortcut.

The fixture invokes the actual local IPC preview and commit on the same LocalPeer.
The preview records 32 total, 31 pending, one applied, 32 eligible, zero active and
trusted retention. Commit expires 32; the following ledger preview is empty. The
original real repository query then returns exactly unknown. Android retains the
same encrypted attempt, complete draft and unknown fence, issues no old release
and never replays its upload. A fresh 32-byte value succeeds with a genuine Source
receipt, one SDK result, durable applied tuple and confirmed release. At completion
only the old unresolved attempt remains; pending releases are empty and upload
counts are `[2 begins, 23 chunks, 2 commits]` (old plus fresh).
