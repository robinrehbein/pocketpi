# Remote file mutations design

Status: proposed for review; no implementation or device qualification is implied.

## Goal and scope

Allow an authorized phone or tablet user to create, rename and delete project files from the file browser on the S25 and Tab. Keep the watch file browser read-only for this increment; assess future watch actions individually for their usefulness on a small display. Deliver this in bounded stages: first create a regular text file, then rename and delete regular files. The later operations remain part of the goal and require their own capability gates and validation. Empty-directory creation or removal, recursive operations, moving directories, bulk operations, overwriting destinations, Git index manipulation, and arbitrary filesystem access are outside this first scope.

The session's actual folder is the browser root, including when it is below the Git worktree root. Existing project sharing, trust, device/session authority, file-write setting, Git membership and path restrictions remain in force. A device must see a capability before offering an operation; the host independently enforces it. The watch client must not expose write controls or issue these commands through shared client code. This is a client product restriction, not a claim that the host authenticates or enforces a device class; host authorization remains required for every request.

## Existing behavior and constraints

The host resolves the session folder and current project at `packages/pi-atlas/extensions/remote/host/files.ts:458`, validates paths and locates Git at `:467`, and checks write restrictions relative to the worktree, shared project and configured hooks path at `:535`. The shared path shape and deny lists are in `packages/pi-atlas/extensions/remote/protocol/files.ts:283` and `:309`. Existing save checks exact Git listing membership at `host/files.ts:1032`, serializes saves, checks regular single-link owned writable files, uses a temporary file, and rechecks authorization before rename at `:1062` and `:1148`. Its write capability is separate at `protocol/files.ts:33`. These checks provide a starting pattern, not an atomic guarantee against every concurrent local filesystem mutation.

The browser exposes Git-listed tracked and non-ignored untracked files. A newly created path cannot already have exact Git membership, so creation needs a specific policy rather than reusing the existing-file test. After creation it must be visible under that policy. A session rooted in a subdirectory still uses paths relative to that session, while deny rules also apply relative to the worktree and shared project as today. Reject Git failures or ambiguous/truncated answers; do not infer eligibility from an incomplete list.

## Approaches

1. **Node guarded operations, with explicit concurrency limits (recommended initial path).** Extend the existing validation, serialization, access checks, audit and capability patterns. Use exclusive creation and no-overwrite semantics that are actually supported on the host; do not emulate them with a check followed by an overwriting rename. This matches the current stack and enables an early feasibility spike. It cannot promise race-free containment or compare-and-swap against a concurrent local process that can replace path components.
2. **Native POSIX helper after a feasibility assessment.** A small audited helper could walk directories through directory descriptors with no-follow checks and use platform-specific no-replace primitives where supported. It reduces pathname and symlink races but introduces packaging, security review and macOS/Linux platform differences. Held descriptors alone do not prove a directory remains beneath the root if another process moves it, and a pre-operation inode check does not supply a universal atomic compare-and-delete/rename. Assess this option if the threat model requires stronger guarantees; do not silently substitute a weaker fallback.
3. **Require an isolated filesystem namespace or equivalent ownership boundary.** This can strengthen the model against hostile local writers, but portability, operational cost and achievable guarantees require separate investigation. It is not a prerequisite to the proposed initial guarded design, and is not claimed as solved here.

Before enabling any operation on a platform, demonstrate its no-overwrite and failure behavior on that platform. If the required primitive is unavailable, withhold that capability. Local users and processes with write access to the project are concurrent actors; the initial release protects against ordinary stale state and detected races, not an actively malicious same-user process continuously swapping filesystem paths. Communicate this boundary in technical documentation, and do not describe a stat check plus mutation as atomic CAS.

## Authorization and path policy

Every request carries a session ID, operation ID and relative path(s), validated strictly with the same byte limits and segment rules as the browser. Never accept an absolute path or traverse a symlink. Resolve the current session and project afresh; require device authorization, current sharing/trust, the file-write setting and operation capability. Repeat authorization and project access immediately before the filesystem mutation, including after any queue wait. Recheck source and destination parents with the existing real-path and write-deny policy, including the worktree/project roots and current `core.hooksPath`; check both source and destination names for rename. Reject special files, symlinks, hard-linked source files, submodules and nested repository traversal. Keep ownership, permission, size and text restrictions at least as conservative as existing save, unless an explicit later design changes them.

For create, require an existing eligible real parent under the session root; do not create missing parents. Reject an existing destination, including a symlink or differently cased equivalent as decided by the filesystem. Determine using Git whether the proposed path is ignored, inside a nested repository or submodule, or otherwise excluded, and reject it if so. Validate that a successful new file is discoverable by the existing list policy. Apply no-follow and exclusive-create semantics at the final operation; choose restrictive initial mode. Any implementation detail which cannot uphold the policy fails closed.

For rename and delete, require the exact source to be a currently listed tracked or non-ignored untracked regular file. Require a fresh source version from the browser and revalidate it near the operation; a changed or missing source is a conflict. Initially rename changes only the basename within the same existing parent directory. It requires a fresh source file version obtained in a preflight, checks the source and destination names and parent against the deny rules, rejects existing targets, and never overwrites. Moving between parents is deferred to a separately reviewed extension. Case-only renames need explicit platform testing and are refused where the requested no-overwrite semantics cannot be met. Delete removes only the selected regular file, never a directory, and does not invoke Git to stage or discard changes. Tracked changes become ordinary worktree changes; no automatic commit or index update occurs. Symlink and race checks reduce risk but cannot guarantee an atomic source-version predicate against external writers with the current Node APIs.

## Operation identity, recovery and outcomes

Each mutation uses a cryptographically random operation ID. Its uniqueness key is the authenticated device identity plus operation ID, independent of session, project or operation kind. Bind the key to a canonical fingerprint containing the session/project scope, operation kind, paths and all preconditions. A duplicate key with the same fingerprint returns its recorded result or state; reuse with any different fingerprint is rejected. Do not use the existing in-memory expiring command ledger as durable exactly-once evidence.

Persist a reservation before mutation. Use a single-writer host process for the journal and its mutations; prevent a second process from opening it for writes, and fail closed if exclusive ownership cannot be established. A terminal applied result is recorded only after the operation and its intended sync steps complete. A known refusal before any possible effect may be recorded as terminal refused. If the effect may have occurred but sync, result recording, or a later check fails, mark or recover the reservation as **unknown**. A crash between filesystem mutation and journal persistence is likewise unknown. Journal and filesystem are not a single transaction; an applied result is not universal proof of survival under every filesystem or power-loss condition. Specify and test the sync and durability contract per supported platform.

Recheck current device authority, session, project sharing and trust on every status or result lookup. Permit a currently authorized user to recover an existing operation even when its write switch is now off or the capability is no longer advertised; recovery does not grant permission to initiate a mutation. Revoked access returns forbidden, not unknown. An operation ID is not a bearer credential.

An unresolved reservation must appear in a discoverable pending/recovery surface after reconnect or restart, scoped to the authorized device and session. Never automatically replay an unknown operation. The user refreshes and inspects the relevant paths, then explicitly acknowledges the uncertainty; observed presence or absence is not proof of which actor caused it. Acknowledgement must retain the original operation ID and tombstone, not convert it into success or permit the same ID to execute again. A subsequent user decision to act is a new operation with fresh preconditions and a new ID.

Keep detailed terminal results for a defined client retry/recovery horizon and retain a durable per-key tombstone afterward, so an old random ID cannot be mistaken for a new request. Once detailed evidence expires, return expired/unknown for that key. Define bounded capacity before implementation; tombstones consume capacity, so when the limit is reached apply backpressure rather than silently forgetting them. Apply the same fail-closed behavior before reservation or mutation when the journal is unavailable, corrupt, missing unexpectedly, or its exclusive ownership and continuity cannot be established. A future bounded reclamation scheme requires an explicit durable namespace or epoch protocol that rejects old IDs; it is not assumed here. Loss of the journal must not silently reset the deduplication namespace or permit blind replay. Log applied/refused/unknown outcomes without file content; if authorization ends after a mutation, audit the landed action even if result delivery is refused.

## Client interaction

On S25 and Tab show create in an eligible folder, and rename/delete on eligible file rows only when advertised. Validate names locally for immediate feedback, while treating the host as authoritative. Create prompts for one filename and creates an empty UTF-8 file; refresh and open it only after a confirmed success. Rename prompts for a new basename in the same parent, obtains a fresh source version before submission and refreshes the listing. Failures explain conflict, unavailable capability, permission or unsupported filesystem as appropriate without exposing sensitive host paths.

Delete requires an explicit confirmation naming the exact relative path. The default action is cancel; the confirmed action deletes only that file. Before rename or delete, check open and parked/recovery drafts and pending saves for the source; before rename, also check the destination for an existing draft or pending save. Block the operation until affected pending saves settle and every affected dirty draft has been saved successfully or explicitly discarded. A failed save or conflict must preserve all drafts, including parked/recovery drafts. A successful rename must update or close the editor consistently; an unknown mutation outcome keeps the draft and requires a refresh and user inspection. Do not optimistically remove or rename an item on an ambiguous response. Handle disconnects and repeated taps using the same operation ID and status flow.

## Rollout and verification

1. Probe Node/platform no-replace primitives and Git ignore/nested-repository behavior in disposable fixtures on both macOS and Linux; define precise supported filesystems and fail-closed responses. Assess a native helper if Node cannot provide a required primitive. Leave that platform capability disabled when feasibility is not demonstrated; an unsupported platform means the full goal remains incomplete. Implement the durable operation protocol and the narrow create capability first. Keep capabilities off until host, protocol and phone/tablet support are ready.
2. Add rename and delete behind separately advertised capabilities after no-overwrite and stale-source behavior are established on each host. No release should imply that create alone completes the requested feature.
3. Verify S25 and Tab on real devices with a real host, including disconnect/reconnect and dirty drafts. Verify watch remains read-only. Emulator and unit evidence must be reported separately from actual-device qualification.

Tests should cover strict wire validation; session subdirectories and linked worktrees; tracked/untracked/ignored files, nested repositories and submodules; deny rules from session, worktree, project and configured hooks paths; symlinks, hard links, special files, ownership, permissions and inaccessible parents; name collisions and case behavior; source-version conflicts, overlapping requests and host queueing; authorization revocation and setting changes before and after mutation; exclusive no-overwrite under concurrent creators; rename/delete failure and external path swaps at injectable boundaries. Such race tests establish behavior at tested boundaries, not a universal proof against hostile local writers.

Test durable reservations, repeated IDs and fingerprint mismatch, process crash at each persistence/mutation boundary, unknown outcomes, retention and exhausted storage. Test client confirmations, dirty draft preservation, unknown-result recovery and capability absence on phone, tablet and watch. Record supported platform/filesystem results and unresolved native-helper decisions before enabling each capability.
