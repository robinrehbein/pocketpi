# Owned Mac iOS simulator backend: integration proposal

Scope: design only; the public XCTest bridge probe is a prerequisite. Do not claim an interactive or feature-equivalent backend until the probe and real end-to-end gates pass. No private frameworks. The host code below is in `/private/tmp/pi-remote-environment/packages/pi-atlas/extensions/remote/`; the client paths are in the PocketPi checkout.

## Boundary and policy

- In `host/emulator-policy.ts`, keep the exact existing untagged Android configuration accepted and stored unchanged. Parse internally into a discriminated union: legacy untagged or explicitly tagged `android`, and explicitly tagged `ios`/`ownedMac`. iOS fields should be minimal owner-configured values: exact simulator UDID, trusted Xcode/runner location and private state directory, plus only bridge parameters actually proven necessary by the probe. Reject unknown fields, malformed UUIDs, duplicate IDs/state directories and duplicate canonicalized UDIDs across profiles. No remote-supplied executable, target, arguments or endpoint. Include platform and every relevant field in `emulatorProfileKey`, so policy edits revoke active handles. Preserve Android path/port uniqueness and validation; Darwin-only iOS preflight must fail closed without affecting Linux Android.
- Require explicit owner opt-in (`emulatorControl`, a locally configured iOS profile, and the existing project/device/profile grant); no discovery/auto-enrolment of arbitrary simulators. Preserve existing agent authorization policy, project checks, policy revalidation, and guards. Specify whether already-booted simulators are admissible: safest initial policy is reject them and only stop a simulator this runtime booted, with an exclusive per-UDID lock. A lock does not itself prove identity or prevent outside tools changing the simulator; fail closed on unexpected state/identity and never terminate an unrelated process. Do not erase simulator data. Use exact UDID for every simctl/XCTest destination, never `booted`, names, or a first match.
- `host/emulator-coordinator.ts`: generalize `owned`/`failedRuntime` from Android class to a minimal owned runtime interface (`open`, `close`), dispatch by trusted profile tag, preserve permits, stable profile snapshots, tombstones and guard checks. `host/emulator-service.ts`, ownership/leases, input sequence, frame acknowledgements and retention stay shared. `host/emulator-runtime.ts` already defines `OwnedEmulatorHandle`; put iOS implementation in a separate `host/emulator-ios-runtime.ts` implementing the same guard, bounded serial queue, capture confirmation and uncertain-dispatch semantics. Do not weaken Android checks to fit iOS.

## Wire and client compatibility

`protocol/emulator.ts` and PocketPi `src/main/java/de/joinnoah/pi/remote/EmulatorProtocol.kt` strictly reject unknown keys, including profile fields. Adding `platform` or input capabilities to v1 responses breaks existing clients. Keep the existing Android v1 wire and fixture byte-compatible. Introduce a separately negotiated capability/version (or separate explicitly negotiated capability-details command) for platform and supported inputs; only return extended payloads to clients that negotiated it. Filter iOS profiles from legacy clients unless a compatible honest UX can be guaranteed; verify routing and capability negotiation before settling the exact mechanism. New client `EmulatorClient.kt`/`EmulatorView` stores per-profile supported inputs, and `EmulatorPane.kt` displays only supported buttons. iOS initial set: tap, swipe, Home only if proven; Back and other keys must be visibly unsupported, and the server must reject them before `beforeDispatch` (never translate Back to Home or falsely acknowledge it). For agents and stale/malicious clients enforce the same server-side restriction, with an explicit unsupported error rather than a generic success. Preserve existing Android controls and behavior.

## Coordinates and runner safety

- Existing `EmulatorPane.kt` letterboxes the displayed bitmap and converts its coordinates into `displayWidth`/`displayHeight`; `EmulatorService.captureAccess` only permits coordinates after that participant acknowledges the frame and tracks generation/revision. iOS must define display dimensions in the same oriented coordinate space as its screenshot and translate deterministically to XCTest's proven screen-point coordinate system, including scale, orientation and edges. Do not assume screenshot pixels equal XCTest points or rotate twice. Bounds-check both endpoints and preserve duration only if XCTest can implement it faithfully. Capture geometry before and after screenshot; invalidate confirmation on any geometry/orientation/scale change, and recheck immediately before mutation. If stable mapping cannot be established, reject coordinate input. Respect frame limits and aspect-ratio consistency after resizing.
- Launch an owner-trusted, fixed XCTest runner with exact `-destination` UDID, no shell interpolation, bounded startup and operations, least inherited environment, private runtime data, and no arbitrary network command. Bridge listens on `127.0.0.1` only (or a private Unix socket if probe supports it), uses a fresh cryptographically random per-run secret delivered via an appropriate private channel, authenticates every bounded request and rejects unauthenticated/replayed requests. Authenticate/identify the actual runner endpoint before allowing capture or input; a random port and loopback alone do not authenticate. Treat same-user process compromise as outside this mechanism's guarantee unless stronger OS isolation is demonstrated. Never expose token in logs or command line.
- Guard policy and exact UDID before launch, connect, capture and immediately before dispatch; post-dispatch policy loss, timeout or runner crash is `EmulatorInputUncertain` and must never auto-replay. Track spawned runner and its descendants through a provable lifecycle; cancel queued operations, close transport, terminate only owned children, wait for confirmed exit, release lock/permit only when cleanup confirmed, otherwise retain tombstone. Test crash, revocation and open/close races. Do not imply simulator shutdown occurred when ownership/termination is unproven.

## Required gates

1. Probe public XCTest API availability and actual runner reachability, target identity, screenshot orientation/pixel dimensions, coordinate scale, tap/swipe duration and Home across a real Mac simulator; establish whether XCTest can reliably drive the required foreground apps. Record Xcode/macOS/simulator versions and evidence. Unsupported capability remains disabled.
2. Policy tests (`host/emulator-policy_test.ts`): old Android config unchanged, tagged union and unknown tags/fields, duplicate normalized UDID and state paths, profile-key changes, fail-closed host/path checks, owner opt-in/grant/revocation. Linux Android regression.
3. Runtime/coordinator/service tests: exact UDID argv and isolation from another booted simulator, endpoint spoof/auth/replay rejection, command bounds, geometry changes, unsupported keys before dispatch, ownership/grant revocation race, uncertain outcomes, no replay, process failure/cleanup and retained lock/permit on unconfirmed cleanup. Existing Android integration tests remain green.
4. Protocol and app tests: existing v1 fixture and legacy clients, negotiated extended capability and profile filtering, per-platform buttons, stale frame/generation rejection, aspect-fit mapping including rotated/scaled/edge cases. Verify `EmulatorPaneTest.kt` and client parser/controller tests.
5. Real end-to-end on Mac: paired PocketPi client opens the specifically granted simulator, receives an acknowledged frame, tap/swipe/Home visibly affect that same simulator, a second simulator remains untouched, Back is unavailable, rotation/resize cannot misdirect input, revocation stops access and cleanup leaves no owned runner. Report separately unit, Mac simulator and actual handset results; no claim of real-device validation without it.

## Concrete negotiation refinement

Recommend one negotiated metadata extension with a distinct list command; all opened/status/control/frame messages remain v1. This avoids changing the shared service's lease or stream protocol:

1. New client appends `emulator_profiles.v2` to the existing `projects.list` request ID `capabilities.v3:optin=...:<nonce>` in `DefaultRemoteRepository.kt`. Extend `protocol/parse.ts` opt-in parser and add `session.emulator.profiles.v2` capability. A capable, eligible host advertises this in the same bounded v3 `projects` result together with `session.emulator.v1`. Old hosts ignore the name; old clients do not opt in. Client uses v2 only after receiving the capability, else uses unchanged v1.
2. In `host/daemon.ts` set a new per-peer `emulatorProfilesV2Negotiated` only in the existing successful result outbox `onSent`, when the sent result actually contains the v2 capability and the matching opt-in; do not set it while constructing/enqueuing the result. It is connection-local and cleared on reconnect. Existing `emulatorNegotiated` is currently set during result construction at lines near 6554, before delivery; do not copy that behavior for v2. A command arriving before `onSent` fails closed. Enforce current policy/grants independently for every operation; the flag is a protocol compatibility gate, not authority. Define repeated negotiations consistently, preferably monotonic for a connection after successful delivery; policy revocation still immediately takes effect.
3. Add strict command `{type:"emulator.list.v2", requestId, sessionId}` and strict result `{kind:"emulator.profiles.v2", profiles:[{id,label,platform:"android"|"ios", inputs:["tap","swipe","Home", ...]}]}`. Input names are a closed bounded set from the existing input wire; include only tested capabilities, Android preserving all current keys. Service derives the metadata from server-owned profile/backend and a v2 list result from the same authorized profile selection; do not trust metadata supplied by the peer. Extend `protocol/parse.ts`, `protocol/emulator.ts`, Kotlin `EmulatorProtocol.kt` and fixtures. Separate `kind` lets strict v1 parsers remain untouched for v1 payloads; do not add fields to `emulator.profiles`, status or state events.
4. Always filter iOS out of legacy `emulator.list`; explicitly reject `emulator.open` for iOS unless this particular device peer has the delivered v2 negotiation, even when the caller guesses an ID. Pass a trusted per-call supported-platform scope from daemon to coordinator/service, apply it in list *and* open against the current policy immediately before runtime creation, and bind/recheck it during asynchronous open and result delivery. Keep existing project/device grants and profile-key guards; v2 negotiation never authorizes access. Agents use a separate explicit server-owned capability/scope decision at their dispatch entry, with no implicit inheritance from a phone peer. This can be one optional context argument, not a duplicated service or a client-controlled field.
5. At runtime reject unsupported inputs before mutation/`beforeDispatch` for all callers. `EmulatorPane.kt` maps selected v2 profile metadata to the current profile and only renders supported buttons. For v1 fallback preserve the current Android UI. Unsupported keys must have a clear host error for stale/malicious clients, with no automatic retry.

Important delivery details: daemon's device emulator path uses `this.send(...)`, whereas the existing `projects.list` result has a concrete `peer.outbox.enqueue` `onSent` hook; use that established negotiation hook, not a guess based on a request ID attached to arbitrary commands. Recheck the final actually emitted capability list and any delivery projection rather than merely the pre-send intention. This refinement is an API proposal; exact metadata and mapping remain contingent on the live XCTest probe.
