# Paged editor: positive durable outcomes

**Status: private implementation exists; qualification is in progress. Public paged-editor and outcome gates remain OFF.** See [implementation evidence and limits](../testing/paged-editor-positive-outcomes.md). This amends the [paged editor contract](2026-11-01-paged-editor-contract.md) and [durable recovery plan](2026-11-01-paged-editor-durable-recovery.md); existing gates and unknown-outcome quarantine continue to apply. It is a narrow first step toward recovery, not a claim that every lost ACK can be reconciled.

## Decision and scope

Add a separately negotiated, read-only query for one **positive** outcome: the Host has durably recorded a matching, validated acknowledgement from the original Native or RPC editor owner. A missing, expired, inaccessible, incomplete, corrupt, mismatched or otherwise unverifiable record is **unknown**, never a negative outcome and never permission to retry or clear the Android fence. No `not_applied`, replay, cancellation, new settlement or authority is provided by this query. Do not infer anything from question absence, a new grant, a generic close or the current source.

The alternative of retaining only the current live ACK cannot reconcile a lost response after Android death. A complete positive/negative protocol would additionally require durable, atomic owner settlement and proof that no write is in flight across every Host and source restart; that is not established here. The positive-only contract is useful even though crashes can leave permanent unknowns.

## Immutable binding and negotiation

Use the existing `commitRequestId` as the **single cross-layer commit identity**, not another wire attempt ID. It is randomly allocated before Android's commit reservation and already appears as the commit request ID. For this extension it must remain unchanged through Host dispatch, source IPC/bridge acknowledgement, durable record and query. Scope its uniqueness to the authenticated route/device and owner incarnation; reject any reuse with a different immutable tuple. Android's existing `attemptId` remains a local journal record key for serialized cleanup and is not represented as a second wire identity. A transport request ID used for the later query is separate and fresh; it never replaces `commitRequestId`.

An immutable owner-incarnation ID is generated by the source for each actual editor ownership incarnation, changes on replacement/restart even for identical question bytes, and is conveyed and verified through the negotiated Native/RPC owner bridge. The Host binds it to its own authenticated source peer/epoch and exact question and projects it only under the new capability. It is an opaque identifier, not a bearer token or authority. Its ID grammar and length use the existing bounded editor ID rules; collision-resistant generation and non-reuse are mandatory. A reconnect/new grant may refer to the same still-live owner incarnation, while a replacement must never do so. If either path cannot establish this binding it must not advertise this capability for that owner.

The immutable receipt tuple is: authenticated paired route and device identity; session and question IDs; owner-incarnation ID; original connection-issued grant ID as captured evidence; upload ID; `commitRequestId`; final strict UTF-8 byte count and SHA-256. The Host derives authority from its actual authenticated connection, grant mapping, source and settlement state, not fields asserted by Android. The source ACK must bind the same owner incarnation, commit ID, upload ID, byte count and hash to its actual original editor settlement. The Host validates that ACK against its captured tuple and peer before recording it. A matching hash or question ID alone is insufficient.

Introduce an independent versioned Host capability and client opt-in, for example `session.question_editor_positive_outcome.v1` / `question_editor_positive_outcome.v1`, alongside—not implied by—the paged capability. Require the corresponding versioned Native or RPC bridge acknowledgement and test each independently. When all apply, include `editorOwnerIncarnationId` in the current authorized question projection and capture it with the source and grant **before** the Android journal reservation and possible commit write. The versioned commit/bridge payload carries the stable commit ID and owner incarnation; enforce exact validation at each hop. A current source read and grant remain necessary for a new upload, but are not required to use a later authenticated receipt query. If negotiation is absent, retain existing behavior and indefinite quarantine for uncertain commits; do not infer this extension from the base paged capability.

## Host durable barrier, bounds and query

For a negotiated commit, the Host serializes a durable, bounded receipt ledger. Before dispatch to the owner it atomically reserves a fixed-size slot containing the full immutable tuple and a `pending` state. A full, unreadable or unwritable ledger refuses the commit **before possible owner write**; it must never evict an unexpired record to make room. Only after an exact, authenticated original-owner ACK does the Host atomically replace that reservation with `applied` and durably flush it before reporting `accepted` to Android. If this update fails, or the Host crashes after possible owner write and before durable `applied`, the outcome is unknown even if the source actually settled. On restart, `pending` remains unknown and must not cause a resend. ACK processing and receipt persistence must remain associated with the captured owner even if its normal close races the ACK; a replacement question cannot satisfy the reservation.

Initial policy for the implementation slice: at most 32 total pending and applied entries per authenticated device and 1,024 total across the Host, each at most 4 KiB of validated metadata and no editor text. Both entry limits and a 4 MiB aggregate metadata limit are enforced atomically at admission, before possible owner dispatch; a full ledger returns a bounded capacity refusal. Pending entries occupy capacity just like positive entries. Unreleased entries are retained for **at least 30 days** from reservation. No record is evicted early to admit another commit, or because of restart, question close, device reconnect or draft expiry. After that window an explicit expiry may reclaim either state, but subsequent queries return unknown, not a negative result. Expiry requires a trustworthy elapsed-retention calculation across restart; clock rollback or uncertain time must retain the entry and apply backpressure. Disk/full, corruption, key loss and storage failures similarly fail closed. These bounds and retention are design defaults requiring resource qualification, not a guarantee that an outcome is available forever.

To permit continuous successful use without waiting 30 days, add a separately negotiated, authenticated receipt release operation, for example `session.question.editor.outcome.release`. It is distinct from the read-only query. Only **after** Android has verified the exact `applied` tuple and atomically removed its corresponding fence may it request release, supplying that same immutable tuple. The Host treats release as that authenticated client's declaration of completed local cleanup; it cannot independently inspect the Android journal. The Host deletes only the fully matching `applied` entry belonging to the authenticated route/device; a pending entry, different tuple or other device must never be deleted. The operation is idempotent: an already absent entry receives the same generic completion as a matching deletion, without disclosing another device's records or treating absence as an outcome. A release must not contact the owner or settle, cancel or replay anything. If the client dies after local cleanup and before release, the v3 journal retains the queued receipt and retries it after matching authentication. A failed release remains queued. An unavailable or no-longer-authorized scope can still retain a Host slot until successful release or separately qualified expiry; the current Host has no automatic expiry. Release is a storage optimization, not a precondition for local cleanup or proof of settlement.

Add a separately authorized query such as `session.question.editor.outcome.get`, with a fresh request ID and the immutable receipt tuple excluding the secret. It is accepted only on the currently authenticated paired route/device and only for that device's own scoped record. It returns `applied` with the complete recorded tuple only when the exact durable positive record exists; all other valid lookups return `unknown` without revealing another device's records. Invalid requests and authentication failures use existing protocol errors and cannot be interpreted as outcomes. Query is read-only: no owner contact, upload, settlement, grant creation, ledger cleanup or retry. Host replacement, ledger loss, retention expiry, or source replacement never converts missing evidence to `not_applied`.

## Android integration and migration

Version the encrypted journal to store the captured owner-incarnation ID, final byte count and hash together with the existing route/session/question, grant, upload, commit ID, exact text and local attempt ID. Reserve that complete tuple atomically before the transport's possible-write boundary. Revalidate the live captured source, owner, grant and selection immediately before dispatch as today. Records from older journal versions lack the owner-incarnation binding: migrate them without discarding their text or fence, mark them **legacy unknown**, and never match them to a new query or infer their owner from the current question. If migration, read, validation or storage fails, preserve the encrypted data and fail closed.

The initial implementation deliberately performs no automatic ledger expiry; pending or unreleased records retain capacity indefinitely until separately qualified cleanup exists. Release retry now uses the encrypted v3 metadata queue, qualified within the linked Android-death cases. These are open resource/recovery gates, not an implementation of the proposed 30-day expiry policy.

After reconnect and capability negotiation, Android may issue the read-only query for a fully bound record. Validate the returned tuple byte-for-byte against that exact journal record and the currently authenticated route/device; reject wrong owner, grant, commit, upload, size, hash or session. Retire only that exact attempt after successful atomic durable journal cleanup, using the existing serialized cleanup/failure path. In that same write, reclaim its same-key draft only if both text and timestamp exactly match the values stored by reservation; preserve any changed or newer draft and all other keys. This prevents completed drafts from exhausting the bounded journal without discarding unsubmitted work. Only after that durable removal may the client send the separately authenticated exact-tuple release; release failure does not recreate the fence or repeat the commit. Failed cleanup retains the fence and a local cleanup retry; it must not issue a commit again. Unknown, expired or legacy records remain visibly quarantined; an explicit user-controlled support/recovery path must not silently assert non-application. Current draft restoration and proof-independent authorized Cancel rules remain unchanged.

## Next implementation slice: durable release retry

The successful private restart cases exposed the remaining capacity gap: local cleanup and release are separate, so a process can die between them. Add a bounded metadata-only pending-release queue to the existing encrypted journal. Do not retain editor text in that queue or infer a release from a generic close.

- Version the journal again and read v1/v2 without changing their attempts, text or legacy uncertainty. A new atomic operation must compare the complete expected bound attempt, remove only it and enqueue its exact receipt in the same disk write after a validated positive proof. Proved non-dispatch cleanup does not enqueue a release.
- Bound the queue independently by count and encoded bytes, with per-route/device admission consistent with Host capacity. If queue admission fails, retain the attempt and visible cleanup retry; do not silently discard a release record to admit another one.
- After current authentication and independent capability negotiation, retry queued releases only on the matching route/device, using fresh request IDs and a possible-write guard. A positively correlated idempotent release response permits atomic removal of that exact queued request; failure, disconnect or process death leaves it queued. Release never repeats an editor commit. Host pending/unknown outcome protection stays unchanged.
- Qualify process death before/after the combined cleanup/enqueue barrier, after Host deletion before ACK, after ACK before local queue removal, navigation/reconnect and route/device replacement, corruption and queue capacity. Require successful continuous use beyond 32 edits without leaking applied Host entries. Missing Host history remains unknown and does not become a definite negative outcome.

The core queue is implemented and has scoped Native/RPC Android-death evidence in the implementation notes. It does not replace the separate actual Host-process restart and persistence-crash qualification.
